# ASMlab 서버형 웹사이트 / Raspberry Pi 5 개발 계획

**문서 버전:** 0.1 / 2026-09-23  
**기준 제품:** ASMlab v0.1.1 Native Gate  
**상태:** 기획만 완료. 구현·장비 이전·공개 배포 미실행.  
**사용자가 고려 중인 장비:** Raspberry Pi 5 16GB  
**현재 우선순위:** x86-64 Native Gate → 런타임 경계 정비. Pi 이전을 지금 시작하지 않는다.

## 1. 목적과 현재 결정

목표는 Windows·macOS·Linux 등의 브라우저에서 수식을 입력하고 2D/3D 그래프, AST, 실제 계산 명령과 SIMD 변화를 함께 살펴보는 서버형 수치 작업환경이다. 사용자에게 Linux나 ASMlab 실행 파일 설치를 요구하지 않는 이용 형태를 지향한다.

이번 결정은 **관련 설계를 보관하되 현재 x86 코어 개발과 분리한다**는 것이다. v0.1.1에는 HTML/JS 프런트엔드, API 서버, 네트워크 리스너, ARM64 코드, plot 명령, Pi 배포 파일을 넣지 않는다. 아래 내용은 후속 구현의 제안이며 현재 사용 가능한 기능이 아니다.

## 2. 하드웨어·ISA 조건

Pi 5는 Cortex-A76 기반 ARM64 플랫폼이며 NASM은 x86 계열 어셈블러이다.[R1][R2] 지금의 Linux x86-64 ELF를 Pi의 ARM64 운영체제에서 그대로 네이티브 실행할 수 있다고 가정하지 않는다. 메모리 16GB는 ISA 호환성의 해결책이 아니다.

| 선택지 | 코어 구현 | 관찰 대상 | 장단점과 조건 |
|---|---|---|---|
| Pi 단독 네이티브 | AArch64 어셈블리 별도 포팅 | Pi의 실제 ARM SIMD·FP 상태 | 단독 운영 가능성을 시험할 주 경로. 포팅 비용이 큼 |
| Pi 웹 계층 + x86 서버 | 현재 NASM 엔진 유지 | 원격 x86 CPU XMM/MXCSR | 기존 코드 재사용. 별도 계산 장비와 내부 통신 필요 |
| Pi에서 x86 에뮬레이션 | QEMU 등에서 x86 실행 | 에뮬레이터의 가상 x86 상태 | 호환성 실험용. 실행·성능을 따로 측정하며 네이티브로 표시하지 않음 |

**현재 선택 확정 없음.** Pi 단독 운영을 최우선으로 확정하면 ARM64 백엔드를 채택하고, NASM-only 조건을 최우선으로 유지하면 별도 x86 계산 서버를 채택한다. 에뮬레이션으로 Native Gate/실제 ARM 관찰 조건을 대체하지 않는다.[R7]

웹 서비스 전체에 순수 어셈블리를 강제하지 않는다. 제안 경계는 **Assembly-only 계산 코어 + 별도 서비스/프런트엔드**다. Python·Node·웹 서버가 있더라도 수식의 실제 계산을 대신하지 않는 서비스 역할과 명확하게 구분한다. 구체적인 서비스 스택은 구현 착수 때 선택한다.

## 3. 승인할 아키텍처 경계

```text
접속자의 브라우저
  입력 / 히스토리 / AST / 명령·SIMD / 2D·3D 그래프
          |
          | HTTPS, 인증, 요청 ID
          v
웹 진입 계층
  TLS / 정적 자산 / 인증 / 용량·빈도 제한
          |
          v
계산 조정 계층
  세션 / 작업공간 스냅샷 / 대기열 / timeout / 취소
          |
          | 제한된 IPC, 명시적인 데이터 스키마
          v
격리된 ASMlab worker
  parser / evaluator / numeric kernel / actual trace
          |
          v
결과 값 / 표본 좌표 / 오류 / trace chunk
```

계산 코어는 웹 서버를 몰라도 CLI와 테스트에서 실행할 수 있게 유지한다. TLS나 HTTP 파서를 직접 어셈블리로 작성하는 것을 코어 독립성의 완료 조건으로 삼지 않는다. 검증된 리버스 프록시를 사용하는 운영안을 검토한다.[R6]

현재 ASMlab은 전역 상태와 고정 arena를 사용하는 단일 프로세스용 프로그램이다. 같은 프로세스에 여러 요청을 병렬로 호출할 수 있다고 가정하지 않는다. 초기 서버는 작업별 프로세스 또는 명확한 세션별 워커 정책을 사용하고, 리셋·수명·공유 여부를 먼저 검증한다.

## 4. ARM64 포팅의 실제 범위

NASM 명령 몇 개를 ARM 명령으로 바꾸는 작업이 아니다. 파서·런타임도 어셈블리이므로 ISA별 구현이 필요하다. 먼저 언어와 알고리즘을 명세로 고정해 구현 차이와 언어 변경을 분리한다.

| 계층 | 보존할 계약 | ARM64 구현 작업 |
|---|---|---|
| 프로그램 진입·OS | 오류/종료 코드·입출력 | AArch64 진입 스택·Linux syscall·호출 규약 |
| 수식 언어 | 토큰·우선순위·오류 위치 | lexer/parser/AST/evaluator 이식 |
| 숫자 처리 | binary64·decimal 정책 | 정수 보조·비트 변환·ARM 부동소수점 환경 |
| Value/작업공간 | shape·소유권·대입 롤백 | 포인터·정렬·arena 구현 및 검사 |
| 계산 커널 | 수학 알고리즘·정의역·오차 | scalar·Advanced SIMD 명령 구현 |
| 추적 | 실제 실행 입력/출력 비트 | ARM 명령 위치·V 레지스터·FPCR/FPSR 캡처 |
| 저장·프로토콜 | 버전과 의미 | ISA 독립 메타데이터와 ISA별 raw payload |

AArch64의 SIMD/FP 레지스터와 FPCR/FPSR 규칙은 ARM의 호출 규약을 기준으로 설계한다.[R3] x86의 MXCSR 값을 ARM 레지스터 값처럼 복사하지 않는다. 아키텍처별 예외 플래그와 반올림 정책은 별도 원시 필드와 정규화된 설명을 함께 둔다.

x86·ARM 알고리즘 비교는 같은 연산 순서에서는 비트 일치 가능 여부를 시험하되 이를 모든 커널에 미리 강제하지 않는다. FMA, 합산 순서, 예외 플래그 차이를 구분하고 함수별 오차 기준을 적용한다. 기존 x86 구현과 테스트 corpus를 비교 기준으로 보존한다.

## 5. 실행 관찰의 진실성 계약

모든 실행에는 다음 메타데이터를 제안한다. 이 스키마는 아직 구현되지 않았다.

```text
schema_version, request_id, run_id, parent_run_id
engine_version, build_id, backend_isa
execution_kind: native | emulated
execution_location: server
numeric_contract_id, fp_policy
source_hash, workspace_snapshot_id
capture_policy, retained_frames, dropped_frames
```

실제 관찰 payload는 `opcode/site_id`, `AST node/source span`, 피연산자 레지스터 식별자·폭·유효 lane, 입력/출력 raw bits, ISA별 제어/상태를 담는다. ASLR을 사용하는 후속 서버는 원시 서버 주소를 외부에 그대로 공개하기보다 빌드 ID와 모듈 내 offset/site ID를 연결하고, 내부에서 역어셈블 대조할 수 있게 한다. 현재 non-PIE 데스크톱 관찰 주소를 서버의 보안 설계로 간주하지 않는다.

- x86 native: 서버에서 실제 캡처한 XMM/MXCSR.
- ARM native: Pi 등 ARM 서버에서 실제 캡처한 V 레지스터/FP 상태.
- 에뮬레이션: 가상 x86 상태임을 명시.
- 브라우저는 캡처 소비자이며 사용자 PC 레지스터를 직접 읽었다고 표시하지 않음.

추적 대상이 제한되어 있으면 전체 CPU 명령 실행을 기록한 것으로 설명하지 않는다. 원래 실행에서 보관하지 않은 점을 선택했을 때는 저장된 입력·작업공간으로 재실행하고 `parent_run_id`와 **재실행 기록** 표시를 붙인다. 다른 실행의 값을 원본 기록처럼 합치지 않는다.

## 6. API와 세션의 제안 범위

초기 API는 실행·상태 확인·결과·추적 chunk·취소만 제공한다. 임의 어셈블리 업로드, 셸 명령, 프로세스 실행, 사용자 지정 파일 경로 읽기, 동적 네이티브 라이브러리 로딩은 제공하지 않는다.

```text
POST   /api/v1/runs              실행 요청 / 제한된 수식과 snapshot
GET    /api/v1/runs/{id}         대기·실행·완료·오류 상태
GET    /api/v1/runs/{id}/result  결과와 그래프 표본
GET    /api/v1/runs/{id}/trace   cursor 기반 제한된 trace chunk
DELETE /api/v1/runs/{id}         취소 요청
```

경로·스키마는 설계 초안이며 v0.1.1에는 엔드포인트가 없다. 기존 `--json` 결과는 계산 성공/오류만 표현하므로 이것만으로 서버 API나 trace API가 완성되었다고 간주하지 않는다.

동일 세션의 대입 순서를 보존하기 위해 작업공간 generation을 검사하고, stale request를 구분한다. 취소·timeout·메모리 부족은 미완성 대입을 commit하지 않는다. `ans`와 대상 변수를 함께 갱신한다. 독립 사용자 간 AST/변수/trace가 섞이지 않는 시험을 필수로 둔다.

네트워크 프로토콜에서는 표본·결과의 float64와 trace raw bits를 구분한다. 64비트 비트패턴을 JavaScript 일반 정수로 전달하지 않고 16진수 문자열이나 버전·endianness가 있는 이진 payload를 사용한다. JSON 입력/출력의 길이·깊이·차원 제한을 검사한다.

## 7. 2D/3D 그래프 설계

수학 표본은 ASMlab이 계산하고 브라우저가 표시한다. WebGL을 사용하는 경우 화면 변환·삼각형 렌더링은 클라이언트 그래픽 계층이며 NASM 수치 커널이 아니다.[R4] Pi에서 매 프레임 이미지를 만들어 스트리밍하는 것을 초기 구조로 삼지 않는다.

| 단계 | 제안 기능 | 코어 필요 기능 |
|---|---|---|
| P1 | SVG 저장, 2D 선 그래프 | 표본 생성, 축 범위, 유효 구간 분할 |
| P2 | 웹 2D 확대·점 선택·히트맵 | 표본 ID, 데이터 전송, 값·AST 연결 |
| P3 | 3D 곡선·와이어프레임 | x/y/z 배열·격자 |
| P4 | 표면 회전·색상·선택 | mesh payload·정점 인덱스·카메라 UI |
| P5 | 등고선·고급 그래프 | 개별 알고리즘과 정의역/오차 시험 |

SVG는 파일 생성으로도 구현할 수 있다.[R5] 대화형 웹 화면과 독립 파일 내보내기를 구분한다. `plot`, `plot3`, `mesh`, `surf`, `linspace` 등의 이름은 후보 문법이며 현재 interpreter에는 없다. 함수 다인수·동적 배열 도입 시 문법 계약부터 정한다.

그래프의 점 → 표본 ID → source/AST → 캡처 이벤트를 연결한다. GPU 전달 과정에서 float32로 줄인 값이 있다면 툴팁·검증은 원래 float64 데이터를 사용한다. 그래프 축 자동 축척, 겹친 점 선택, 빈 데이터, 극단적 값, NaN/Inf 정책을 정의한다.

`1/x` 등의 불연속 구간을 선으로 가로질러 연결하지 않도록 유효성 마스크·구간 단절을 표현한다. 단순 고정 표본만으로 모든 불연속을 발견할 수 있다고 주장하지 않는다. adaptive sampling은 별도 오차/깊이 제한과 실패 표시를 포함한다. 그래프 표본 하나의 정의역 실패와 일반 표현식 전체 실패의 정책은 분리해 문서화한다.

## 8. 자원 예산과 운영 조건

16GB라는 용량만으로 처리 사용자 수나 응답 시간을 보증하지 않는다. 예를 들어 256×256 높이 배열 한 개의 binary64 데이터는 524,288바이트(0.5MiB)지만 좌표·인덱스·중간 결과·trace·전송 버퍼는 별도다. 이 값은 산술적 크기 예시이며 실제 ASMlab 성능 측정이 아니다.

현재 trace record는 96바이트, 최대 8,192개로 기본 record 공간만 786,432바이트다. 후속 trace v2가 더 많은 레지스터/메타데이터를 담으면 별도 예산이 필요하다. 기존 16×16 자료구조의 상수만 크게 올려 그래프를 구현하지 않는다.

초기 실험은 워커 1개와 요청 대기열부터 시작하는 안을 권장한다. 아래 제한은 구현 시 측정으로 결정하며 현재 서비스의 설정값이 아니다.

| 제한 | 측정·결정할 항목 |
|---|---|
| 입력 | 최대 바이트, AST 노드/깊이, 숫자 토큰 길이 |
| 계산 | 전체 wall time, CPU time, cancellation latency |
| 메모리 | 워커·세션 quota, 배열 원소 수, 중간 결과 |
| 관찰 | 최대 프레임/바이트, chunk 크기, 보존 기간 |
| 그래프 | 최대 표본/삼각형, 클라이언트 GPU 상한, 전송량 |
| 서비스 | 큐 길이, 사용자별 동시 작업, idle 만료 |

64비트 OS, 적절한 전원·냉각·저장 장치를 준비한 실제 Pi에서 측정한다.[R1] 본 문서에서는 구매, OS 설치, 부하 시험을 수행하지 않았다. 명목 CPU/RAM 사양을 처리량 benchmark로 대체하지 않는다.

## 9. 공개 서비스 전 보안·장애 시험

코어는 현재 로컬 교육·연구 MVP이며 보안 sandbox가 아니다. 공개 서비스 승인 전 다음을 구현·시험한다.

격리된 비특권 워커, 네트워크 접근 제한, 읽기 전용 코드, 허용 디렉터리 외 파일 접근 차단, 리소스 제한, timeout 후 워커 폐기·정리, 프로세스 간 데이터 누수 방지가 필요하다. 구체적인 Linux sandbox/cgroup/seccomp 설정은 배포 시 공식 문서와 시험 결과로 확정한다.

웹 계층에는 인증·세션 권한 검사, 상태 변경 요청의 CSRF 방어, 허용 Origin, 출력 escape, 요청/응답 상한, TLS, 로그의 비밀정보 제거가 필요하다. 수식 텍스트를 HTML·터미널 제어문자로 실행하지 않는다. 정적 자산과 사용자 데이터 저장을 분리한다.

잘못된 수식, 과대 배열, 장시간 계산, 반복 취소, worker crash, 디스크 부족, 재시작을 시험한다. 오류 뒤에도 다른 사용자의 작업공간은 유지되어야 한다. 운영 로그는 수식 원문을 무조건 장기 보관하지 않으며 저장 여부·삭제 정책을 명시한다.

## 10. 후속 착수 순서와 통과 조건

| 작업선 | 선행 조건 | 산출물 | 승인 조건 |
|---|---|---|---|
| S0 계획 보존 | 이번 요청 | 본 문서 | **v0.1.1에 포함, 구현 안 함** |
| S1 코어 호출 경계 | Native Gate / rt_* 설계 | 수치·결과·trace 계약 | CLI/테스트와 웹 계층 독립 |
| S2 플랫폼 선택 | Pi 단독 vs NASM-only 결정 | ARM 또는 x86 server 결정 기록 | 관찰 ISA·의존성·비용 경계 확정 |
| S3 선택 백엔드 | 언어·ABI·수치 계약 | ARM 포팅 또는 x86 worker | 전체 corpus, raw-state, 실패 시험 |
| S4 서비스 실험 | worker 격리 | 내부 API·대기열·세션 | 교차 사용자 격리, 취소·quota |
| S5 그래프 | 동적 표본/저장 계약 | 2D → 3D | 좌표 정확도·불연속·trace 연결 |

| S7 제한 공개 | 인증·TLS·운영·복구 | 소규모 beta | 보안/장애/자료 누수 시험 통과 |

v0.1.1에는 S0만 해당한다. 나머지 상태를 완료로 표시하지 않는다. x86 NASM 버전은 비교 기준으로 보존한다. 기존 Level 3 코어 작업과 서버 작업을 같은 PR에 섞지 않고 별도 완료 조건과 검증 보고서로 관리한다.

## 11. 미결정 사항

ARM64 네이티브 포팅 채택 여부, 서비스 스택, 도메인·배포 경로, 인증 방식, 공개 사용자 범위, 세션 지속성, 대규모 trace 보존 정책, 숫자/trace 이진 프로토콜, 클라이언트 그래픽 라이브러리는 구현 착수 시 결정한다. 현재 승인 없는 장비 변경·원격 배포·외부 계정 생성은 하지 않는다.
